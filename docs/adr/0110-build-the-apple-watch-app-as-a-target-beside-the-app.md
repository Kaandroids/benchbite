# 0110. Build the Apple Watch app as a target beside the app

- **Status:** Accepted
- **Date:** 2026-11-10

## Context

Following the workout on the Apple Watch (#470, ADR 0109) needs an app on the watch. A watchOS app is native: SwiftUI, built by Xcode as a target of its own and carried inside the iPhone app. The iPhone app's `ios/` folder is generated by `expo prebuild` and ignored by Git (Continuous Native Generation), so a target added there by hand would be gone at the next prebuild.

## Decision

- **The watch app lives in `targets/watch`,** outside `ios/`, and the config plugin `@bacons/apple-targets` adds it to the Xcode project at each prebuild. Its `expo-target.config.js` sets:
  - the type `watch`, the name `BenchbiteWatch` and the display name Benchbite;
  - watchOS 10;
  - the frameworks SwiftUI and WatchConnectivity.

  The plugin sets the iPhone app as the watch app's companion and embeds it in the iPhone app.

- **Its bundle id sits inside the iPhone app's:** `com.benchbite.app.watchkitapp`, and `com.benchbite.app.dev.watchkitapp` for the development build, which keeps its own identity (ADR 0096).
- **The team that signs it is in `app.json`** (`ios.appleTeamId`), as the plugin needs it for the target. A team id identifies the developer account and is in every signed app, so it is not a secret.
- **The watch speaks the protocol of ADR 0109 in Swift.**
  - `Protocol.swift` decodes the phone's state and builds commands as `src/watch/protocol.ts` defines them. A command goes as JSON with the workout's id beside it, which the phone's module reads without reading the JSON.
  - `PhoneLink.swift` receives the state and sends commands: by message while the phone is reachable, without a reply handler, else by user info transfer.
- **This first app only shows that the two talk to each other:** the set to do next, which the phone finds, and a Done button. The screens of the approved design, the workout session that measures the heart rate, the texts in the user's language and the phone's own screens follow in their own pull requests.

## Alternatives considered

- **A watch target added by hand in `ios/`:** lost at every `expo prebuild --clean`, and nothing in Git would hold it.
- **A config plugin of our own:** it would have to create the target, its build settings, the embedding and the companion settings in the Xcode project, which `@bacons/apple-targets` already does and keeps working with new Xcode versions.
- **Starting the watch app from a template project in Xcode:** a second project to keep beside the generated one, built apart from the iPhone app it must be carried in.

## Consequences

- `targets/` holds the watch app's Swift and its config; a change there or to its config needs a new development build. The plugin makes the watch app's icon from `assets/` at each prebuild, so it is not committed.
- The watch app's messages must keep to `src/watch/protocol.ts`; a change there is made in `Protocol.swift` too, and raises `PROTOCOL_VERSION` on both sides.
- In the simulators, the watch app is installed on the watch simulator from the build's products; on a device, the iPhone installs it on the paired watch (`docs/development.md`).
- Android's watch app (#471) is a Gradle module of a plugin of our own, as `@bacons/apple-targets` covers Apple targets only.
